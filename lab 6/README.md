## 2. Проверка через страницу и Postman

На странице выберите канал, введите получателя и текст, нажмите «Отправить». Вы увидите результат и новую запись в истории. Кнопка «Обновить историю» повторно читает базу. Время в интерфейсе отображается в часовом поясе браузера.

Получатель — произвольная непустая строка: например, адрес email, номер телефона или ID устройства. Формат настоящего адреса/номера не проверяется, поскольку это учебная имитация.

В Postman создайте запрос:

- Метод: **POST**.
- URL: `http://127.0.0.1:5000/api/send-notification`.
- Body → raw → JSON. Postman выставит `Content-Type: application/json`.

```json
{"type": "email", "recipient": "student@example.test", "message": "Проверка лабораторной"}
```

Ожидается HTTP **201** и ответ такой структуры (ID и время будут другими):

```json
{
  "message": "Демонстрационная отправка выполнена.",
  "notification": {
    "id": 1,
    "type": "email",
    "recipient": "student@example.test",
    "message": "Проверка лабораторной",
    "status": "simulated",
    "created_at": "2026-10-14T16:00:00.000000Z"
  }
}
```

Замените `email` на `sms` или `push` для других каналов. `GET /api/notifications` возвращает `{"notifications": [...]}`; новые записи идут первыми. `GET /` возвращает страницу.

Отсутствующие поля, пустые строки, значения другого типа, неизвестный канал, JSON-массив и повреждённый JSON дают **400**, например `{"error": "Некорректный JSON."}`. Ошибка сохранения даёт **500**, выполняется rollback. Все три поля должны быть строками; пробелы по краям убираются. Канал указывается строчными буквами.

## 4. Основные понятия

**Flask** — библиотека Python для веб-приложений. Она принимает HTTP-запрос и выбирает функцию по адресу и методу. **API** — правила общения с программой: здесь это адреса для отправки и чтения уведомлений. **JSON** — текстовый формат передачи данных, например объект с полями `type`, `recipient`, `message`.

**ORM** связывает классы Python с таблицами: объект Notification становится строкой таблицы. Flask-SQLAlchemy подключает SQLAlchemy к Flask и управляет сеансом работы с базой. **SQLite** — база данных в одном локальном файле; отдельный сервер не нужен.

## 5. Singleton и Factory Method

`DatabaseManager.__new__` создаёт менеджер только один раз. `DatabaseManager() is database_manager` возвращает True. Вместе с ним создаётся один объект SQLAlchemy на процесс. Это **не гарантия одного физического соединения**: соединениями управляет SQLAlchemy. Несколько процессов имеют свои экземпляры Singleton.

Менеджер создаётся при импорте `database.py`, но приложение подключается отдельно через `database_manager.init_app(app)`. Поэтому ранее созданный Singleton не пропускает подключение нового приложения. `models.py` импортируется до `db.create_all()`: к моменту создания таблиц ORM уже знает модель. Контекст приложения сообщает ORM, с конфигурацией какой базы работать.

**Simple Factory** обычно содержит один метод с `if/elif`, который напрямую создаёт нужный продукт. **Factory Method** использует наследование: базовый Creator объявляет `create_service`, а EmailCreator, SMSCreator и PushCreator переопределяют его. Общий метод `Creator.send` получает сервис через этот фабричный метод и вызывает его `send`.

В проекте `NotificationFactory` — удобная точка выбора создателя по каналу, то есть сам выбор остаётся простой фабрикой. Создание сервисов выполняют конкретные Creator через Factory Method. Маршрут не создаёт EmailNotificationService напрямую.

## 6. Путь запроса и хранение

1. Форма собирает канал, получателя и сообщение.
2. JavaScript отправляет JSON через fetch в POST API.
3. Flask проверяет JSON и обязательные поля.
4. NotificationFactory выбирает Creator.
5. Creator создаёт сервис, сервис возвращает `simulated`.
6. Notification добавляется в сеанс ORM; commit сохраняет строку SQLite.
7. API возвращает JSON с кодом 201; страница показывает результат.
8. Страница запрашивает GET API и обновляет историю.

При ошибке записи rollback отменяет незавершённую транзакцию, позволяя сеансу продолжить работу. Пользовательский текст в истории вставляется через `textContent`, поэтому `<script>` отображается как текст.

База создаётся автоматически при обычном запуске: **`instance/notifications.db`**, относительно папки проекта. Время сохраняется в UTC; суффикс `Z` в JSON обозначает UTC. Записи остаются после остановки сервера. Посмотреть их можно в истории, через GET API или в программе просмотра SQLite: таблица `notification`, запрос `SELECT * FROM notification ORDER BY id DESC;`. Тесты используют временную базу и не добавляют записи в пользовательскую.

## 9. Подготовка к защите

Разберите `__new__` и `init_app` в database.py; наследование сервисов и Creator в factory.py; проверку JSON, commit/rollback и маршруты в app.py; модель Notification; fetch и textContent в HTML. Умейте показать три отправки, историю и ошибку 400 в Postman.

1. **Какую задачу решает программа?** Имитирует три вида уведомлений и ведёт журнал.
2. **Где Singleton?** В DatabaseManager: повторный вызов возвращает тот же менеджер.
3. **Singleton означает одно соединение?** Нет, один менеджер и объект ORM на процесс; соединениями управляет ORM.
4. **Зачем init_app отдельно?** Singleton мог существовать до приложения; приложение всё равно нужно подключить.
5. **Где Factory Method?** В Creator.create_service и его переопределениях у конкретных создателей.
6. **Чем отличается Simple Factory?** Выбирает продукт в одном месте; Factory Method поручает создание подклассам.
7. **Зачем ORM?** Позволяет работать с таблицей через объекты Python.
8. **Что означают 201, 400 и 500?** Запись создана; входные данные неверны; ошибка сервера/сохранения.
9. **Зачем rollback?** Отменяет неудачную транзакцию и восстанавливает работоспособность сеанса.
10. **Почему сообщение не доставлено?** Сервис имитирует отправку, реальный провайдер не подключён.

«В этой лабораторной работе я реализовал систему уведомлений с тремя каналами: Email, SMS и Push. Пользователь выбирает канал, указывает получателя и сообщение. Приложение проверяет данные, имитирует отправку и сохраняет результат в журнал. Затем пользователь может посмотреть историю уведомлений.

Основная цель работы — показать применение двух порождающих паттернов проектирования: Singleton и Factory Method. Порождающие паттерны описывают, как создавать объекты и управлять их созданием.

Проект работает локально. Для сервера я использовал Python и Flask, для работы с базой — Flask-SQLAlchemy, а для хранения — SQLite. Интерфейс написан на обычных HTML, CSS и JavaScript. Внешние сервисы и отдельный сервер базы данных не нужны.

Flask связывает адрес запроса с функцией Python. SQLite хранит записи в файле. SQLAlchemy — ORM: с её помощью я описываю таблицу классом и работаю с записями как с объектами. Это делает код небольшого учебного проекта понятным и позволяет не писать SQL для каждого действия».

### Как запускается приложение

Покажите функцию `create_app` в `app.py`.

«При запуске `app.py` вызывается функция `create_app`. Она создаёт приложение Flask, задаёт путь к базе и подключает менеджер базы через `init_app`. Модель Notification импортируется заранее, поэтому ORM уже знает о таблице, когда вызывается `create_all`.

Вызов `create_all` создаёт отсутствующие таблицы и не очищает существующие записи. Он не является механизмом миграций: если в дальнейшем менять структуру уже существующей таблицы, потребуется отдельное решение.

Затем приложение запускает локальный сервер на адресе 127.0.0.1 и порту 5000. Функция создания приложения также удобна для тестов: можно создать приложение с отдельной временной базой, не меняя основную конфигурацию».

Здесь полезно различать два понятия: `create_app` — функция создания Flask-приложения, а изучаемый **Factory Method** реализован в классах `Creator` в `factory.py`.

### Почему выбран Singleton

Покажите класс `DatabaseManager` в `database.py`.

«Singleton, или “Одиночка”, нужен здесь для создания одного общего менеджера базы данных в пределах процесса. Разные модули используют один объект SQLAlchemy и одну общую регистрацию моделей.

В Python метод `__new__` отвечает за создание экземпляра. В моём классе он проверяет поле `_instance`. Если экземпляр ещё не создан, создаётся менеджер и объект SQLAlchemy. Если уже создан, возвращается сохранённый экземпляр. Поэтому два вызова `DatabaseManager()` возвращают один и тот же объект. Это проверяется оператором `is` в тестах.

Блокировка `Lock` защищает участок создания: два потока не должны одновременно создать два экземпляра. При этом блокировка не означает, что все операции с базой выполняются под одним общим замком.

Подключение к Flask вынесено в отдельный метод `init_app`. Это важно, потому что менеджер создаётся ещё при импорте модуля, когда приложения Flask может не существовать. Позже мы явно подключаем его к нужному приложению.

Singleton выбран, чтобы продемонстрировать контролируемое создание общего менеджера. Он не гарантирует одно физическое соединение с SQLite: соединениями и сеансами управляет SQLAlchemy. Если запустить несколько процессов, у каждого будет свой менеджер».

Если преподаватель спросит, обязателен ли Singleton для Flask, ответьте: «Нет. Один объект расширения можно хранить на уровне модуля без отдельного Singleton-класса. Здесь класс введён для выполнения учебной задачи и явной демонстрации паттерна. У Singleton есть недостаток: общее состояние может усложнять изоляцию и тестирование, поэтому в тестах я разделяю базы через конфигурацию приложений».

### Почему выбран Factory Method

Покажите `BaseNotificationService`, затем `Creator` и его подклассы в `factory.py`.

«Все уведомления имеют общую операцию — `send`, но относятся к разным каналам. Чтобы маршрут Flask не создавал конкретный сервис напрямую, создание вынесено в отдельные классы.

Абстрактный класс `BaseNotificationService` задаёт общий контракт: сервис должен реализовать метод `send`. Конкретные продукты — `EmailNotificationService`, `SMSNotificationService` и `PushNotificationService`. Сейчас каждый возвращает `simulated`: это намеренная имитация, а не подтверждение доставки.

Абстрактный `Creator` объявляет фабричный метод `create_service`. Классы `EmailCreator`, `SMSCreator` и `PushCreator` переопределяют этот метод и возвращают нужный сервис. Общий метод `Creator.send` вызывает `self.create_service()`, а затем `send` у полученного сервиса.

Это и есть Factory Method: общий алгоритм использует продукт, а конкретный подкласс определяет, какой продукт создать. Например, для SMS цепочка выглядит так: SMSCreator → create_service → SMSNotificationService → send.

Класс `NotificationFactory` выбирает создателя по строке канала через словарь. Сам этот выбор является простой фабрикой. Factory Method находится именно в иерархии Creator, где подклассы переопределяют создание продукта. Поэтому я не называю любой метод со словом factory реализацией Factory Method.

Паттерн выбран потому, что приложение работает с несколькими видами однотипных сервисов. Он отделяет обработку HTTP-запроса от создания сервиса и позволяет расширять набор каналов. Например, для нового канала нужно добавить сервис, создателя и зарегистрировать его, а общий алгоритм отправки и сохранения останется прежним».

Для маленького приложения прямой `if/elif` был бы короче. Здесь дополнительные классы оправданы учебной целью — показать именно Factory Method. При добавлении канала всё равно меняются словарь регистрации и список каналов интерфейса; утверждать, что расширение вообще не требует изменений существующего кода, неправильно.

### Как проходит один запрос

Покажите обработчик `send_notification` и отправьте сообщение через форму.

«Рассмотрим отправку Email. В браузере пользователь заполняет форму. JavaScript собирает объект с полями `type`, `recipient`, `message`, преобразует его в JSON и отправляет через `fetch` методом POST на `/api/send-notification`.

На сервере я сначала проверяю Content-Type и корректность JSON. Затем проверяю, что получен объект, а обязательные поля существуют и содержат непустые строки. Проверка на сервере нужна даже при наличии атрибута `required` в HTML, потому что API можно вызвать напрямую, например через Postman.

После проверки фабрика выбирает EmailCreator. Он создаёт EmailNotificationService, который возвращает результат имитации. Обработчик создаёт объект Notification и добавляет его в сеанс базы. Вызов `commit` завершает транзакцию и сохраняет запись.

При успехе сервер возвращает JSON с записью и HTTP-кодом 201. Интерфейс показывает результат и отдельно запрашивает историю через GET `/api/notifications`. Сервер выбирает записи по времени в порядке убывания, а при одинаковом времени — по ID в порядке убывания. Поэтому новые записи отображаются первыми».

### Что хранится и как обрабатываются ошибки

Покажите модель `Notification` в `models.py` и блок `try/except` в `app.py`.

«Таблица хранит уникальный ID, тип канала, получателя, сообщение, статус и время создания. Метод `to_dict` преобразует запись в обычный словарь, который Flask возвращает в JSON. Время хранится в UTC, а браузер показывает его в местном часовом поясе.

База находится в `instance/notifications.db`. Поскольку данные хранятся в файле, они остаются после остановки и повторного запуска приложения.

Неверный запрос возвращает код 400 и понятное поле `error`. Если при сохранении возникает ошибка SQLAlchemy, приложение вызывает `rollback` и возвращает 500. Rollback отменяет незавершённые изменения и позволяет снова использовать сеанс.

Статус `simulated` означает только успешную обработку учебной имитации. В проекте нет интеграции с почтой, SMS или Push-провайдерами. При подключении реальных сервисов понадобилось бы отдельно продумать ошибки доставки и повторные попытки: транзакция SQLite не может отменить уже отправленное настоящее письмо».

### Интерфейс и проверка работы

«Интерфейс не требует сборки или CDN. HTML задаёт форму и таблицу, CSS — оформление, JavaScript — запросы к API и обновление истории. Пользовательский текст выводится через `textContent`, поэтому введённые HTML-теги не выполняются как код.

Для проверки используются автоматические тесты. Они проверяют три канала, историю и порядок записей, сохранность данных после повторного создания приложения, ошибочные запросы, Singleton, фабрику и rollback. В тесте ошибки базы сбой commit вызывается искусственно; затем проверяется возможность следующей успешной отправки.

Тесты работают с временными базами и не загрязняют пользовательскую историю. Отдельная HTTP-проверка запускает настоящий локальный сервер и обращается к нему запросами. При этом автоматическая проверка HTML и API не заменяет ручную проверку отображения и кликов в браузере».

3. Обновите страницу: записи загрузятся из базы. При необходимости остановите сервер, запустите снова и покажите сохранность истории.
4. В Postman отправьте неизвестный канал `fax` и покажите код 400. Пример корректного запроса есть в разделе 2.

## 12. Краткая шпаргалка перед защитой

| Вопрос | Что сказать |
|---|---|
| Зачем разделять файлы? | У каждого своя ответственность: HTTP, база, модель, создание сервисов и интерфейс. |
| Где здесь абстракция? | BaseNotificationService и Creator задают обязательные методы без конкретного способа создания/отправки. |
| Где полиморфизм? | Creator.send вызывает один и тот же create_service, но у разных подклассов получается разный сервис. |
| Зачем `ABC` и `abstractmethod`? | Они не позволяют создать экземпляр абстрактного класса, пока обязательные методы не реализованы. |
| Почему сервисы пока делают одно и то же? | В учебном режиме все имитируют отправку; классы показывают места для разных реализаций каналов. |
| Почему именно SQLite? | Хранит данные локально в одном файле и не требует настройки отдельного сервера. |
| Чем `add` отличается от `commit`? | add включает объект в сеанс; commit завершает транзакцию и фиксирует изменения. |
| Что означает `app_context`? | Указывает расширениям Flask, с каким приложением и его настройками сейчас работать. |
| Что проверяет `is`? | Что две переменные ссылаются на один объект, а не просто имеют одинаковые значения. |
| Почему нужны тесты ошибок? | Чтобы проверить отказ с понятным ответом и возможность работы после сбоя, а не только успешный сценарий. |
| Можно ли убрать фабрику? | Технически да, но тогда потеряется демонстрация требуемого Factory Method и создание окажется ближе к обработчику. |
| Какие ограничения у проекта? | Нет реальной доставки, авторизации и механизма повторных отправок; используется локальный учебный сервер. |

Короткая формулировка основной идеи: **«Singleton управляет созданием общего менеджера базы, Factory Method поручает подклассам создание сервисов, а Flask связывает интерфейс, проверку данных и сохранение журнала»**.
